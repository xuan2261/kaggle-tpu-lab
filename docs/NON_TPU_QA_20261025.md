## Settings write hardening and remaining risk

`Settings::save_to_path` serializes before staging to an exclusively created
file beside the target and calls `sync_all` before replacement. On Windows,
an existing regular file is replaced with `ReplaceFileW` using a same-directory
recovery backup so the original destination DACL is retained. First creation
uses `MoveFileExW` without `REPLACE_EXISTING`. Failure paths clean up temporary
files only when the old destination is known to remain intact; exceptional
partial replacements retain recoverable copies rather than deleting them.
Regression cases cover valid JSON overwrite, directory/locked destinations,
and replacement of an explicitly protected Windows ACL.
The existing `persist_settings` mutex still commits in-memory values only
after disk persistence returns success.

This is a defense against truncated writes and DACL regression, **not** a full
power-loss or cross-process transaction. Remaining review items include rare
Windows `ReplaceFileW` partial-failure recovery, reparse-point/directory races
in a writable configuration path, external writers outside the single-instance
process, and silent default fallback on malformed JSON. Treat these as future
reliability work before a production hardening claim; never widen filesystem
permissions to mask a save failure.

## Follow-up: Windows replacement security review

The subsequent owner-authorized review found a real regression in Windows file
replacement: a plain rename discarded a deliberately protected destination
DACL. A new isolated `icacls` regression test **failed before** the correction
and **passed afterward**. `ReplaceFileW` with flags `0` preserves the old file's
ACL, and its named backup is retained or restored on the documented partial
failure paths. A separate test checks that recovery cannot overwrite a file
which another writer has already created.
